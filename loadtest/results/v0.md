# Baseline: v0 (legacy code, tag `v0-legacy`)

Run 2026-10-24 on the local compose stack, each app container capped at 0.5 CPU / 512 MB
(`docker-compose.loadtest.yml`), app containers restarted fresh before the run. Raw output in
`v0-editor-load/` and `v0-contest-soak/`.

## Resource usage (peak CPU of the 0.5 CPU cap)

| Container | Editor load CPU avg / peak | Soak CPU avg / peak | Memory |
|---|---|---|---|
| api-gateway | 36% / 52% | 28% / 51% | **grows without bound** (18 → 297 MB) |
| auth-service | 33% / 53% | 17% / 51% | stable, ~60–110 MB |
| code-service | 10% / 28% | 7% / 26% | stable, ~55–70 MB |
| user-service | 7% / 26% | 4% / 15% | stable, ~30–50 MB |

The gateway and auth-service are pinned at their CPU cap: every API request costs a gateway →
auth-service `get-session` call plus a MongoDB session lookup.

## Root causes (fixed in Session 1)

1. **Gateway memory leak → crash.** `api-gateway/src/middlewares/correlation.middleware.ts` re-wraps
   the global `logger.info/warn/error` on every request. After N requests each log call runs N
   nested wrappers and prints all N correlation IDs (a single log line reached hundreds of KB),
   until the V8 heap is exhausted. Causes the 4% error rate, the high gateway CPU, and the memory growth.
2. **Session check on every request.** Better Auth's cookie cache is enabled, but the gateway
   forwards only the session-token cookie, so the cache is never used.
3. **Rate limiter bypassable.** `trust proxy` is `true`, so any client can set `X-Forwarded-For`
   to get a fresh rate-limit bucket (the load test relies on this to simulate distinct users).
4. **Read on every save.** `POST /save` queries MongoDB before writing to Redis.

# v3: after Session 3 (identity-service, gateway session cache)

Same scenarios, settings and hardware caps as [v0](v0.md), [v1](v1.md) and [v2](v2.md) (0.5 CPU /
512 MB per app container, fresh processes), now with three app containers instead of four
(auth-service and user-service merged into identity-service). Dashboard during the runs:
[v3-grafana.png](v3-grafana.png).

What changed for the request path: v2 made a gateway → auth-service HTTP call on **every**
authenticated request. In v3 the gateway caches each validated session in Redis (5 min,
jittered); a ban, sign-out or session revocation clears it immediately.

## Contest soak: 100 users autosaving every 10s (5m)

| Metric | v0 | v1 | v2 | **v3** | Target |
|---|---|---|---|---|---|
| Failed requests | 0% | 0% | 0% | **0%** (0 of 3,100) | < 1% ✅ |
| Save p50 / p95 / p99 | 100 ms / 1.78 s / 5.67 s | 32 ms / 471 ms / 1.14 s | 30 ms / 357 ms / 1.14 s | **13 ms / 235 ms / 2.23 s** | p95 < 200 ms ❌ |
| MongoDB queries during soak | 2,916 | 101 | 101 | **101** | |

The median halved and p95 is down 34%, but the target is still missed and p99 got worse. The cause
is a test artifact: k6 signs up all 100 users first, so their first saves arrive in the same
instant, all miss the empty session cache, and queue at identity-service, which is capped at
0.5 CPU. Prometheus (10 s windows) shows **no save over 500 ms after that first burst**. Real users
open the editor (which warms the cache) well before a contest's first autosave.

### First attempt: a cache stampede

The first v3 run used a fixed 60 s cache TTL and made save p95 **worse** than v2: 691 ms
(p50 15 ms, p99 1.87 s). The dashboard showed why: all 100 users' sessions were cached in the
same second, so they all expired in the same second, once a minute. Each time, 100 database-backed
session checks hit identity-service at once (identity-side p95 648 ms, CPU at its cap). Slow saves
(> 500 ms) came in bursts at 18:22, 18:23, 18:24 and 18:25, a minute apart.

Fix: a 5 min TTL with each entry randomly set to 80–100% of it (jitter), and never longer than the
session's own expiry. A longer TTL is safe because revocation never waits for expiry: ban,
sign-out, revoke-sessions and password change delete the entries explicitly.

## Where the time goes (Prometheus, editor load, p95)

| Layer | v2 | **v3** |
|---|---|---|
| Gateway, `/api/v1/*` as users experience it | 224 ms | **34 ms** |
| └ session check, from the Redis cache | n/a | **4.8 ms** (99.9% of checks) |
| └ session check, asking identity-service (cache miss) | 152 ms (every request) | 62 ms (~15 in 5 min) |
| code-service handlers | 11 ms | 7.6 ms |
| user profile handler (user-service → identity-service) | 12 ms | 9.4 ms |

identity-service handled ~15 session checks during the editor run instead of one per API request
(~12,800). Its CPU averaged 0.10 (peak 0.26) of its 0.5 cap; in v2 auth-service was pinned at the
cap during the save bursts.

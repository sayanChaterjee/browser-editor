# v4: after Session 5 (contest-service split)

Same scenarios, settings and hardware caps as [v3](v3.md) (0.5 CPU / 512 MB per app container,
fresh processes), now with four app containers: contests, submissions and strikes moved from
code-service to contest-service. The editor and save paths didn't change, so this run checks for
regressions rather than expecting gains.

## Editor load: 50 users opening the editor (1m ramp, 3m hold)

| Metric | v2 | v3 | **v4** | Target |
|---|---|---|---|---|
| Failed requests | 0% | 0% | **0%** (0 of 12,884) | < 1% ✅ |
| Throughput | 43.1 req/s | 44.9 req/s | **44.4 req/s** | |
| Profile p95 | 197 ms | 35 ms | **34 ms** | < 500 ms ✅ |
| Project list p95 | 190 ms | 39 ms | **33 ms** | < 500 ms ✅ |
| Open project p95 | 184 ms | 34 ms | **31 ms** | < 500 ms ✅ |
| Gateway memory | 23 → 38 MB | 28 → 37 MB | **27 → 37 MB, 0 restarts** | |

No regression: within run-to-run noise of v3.

## Contest soak: 100 users autosaving every 10s (5m)

| Metric | v2 | v3 | **v4** | Target |
|---|---|---|---|---|
| Failed requests | 0% | 0% | **0%** (0 of 3,100) | < 1% ✅ |
| Save p50 / p95 / p99 | 30 ms / 357 ms / 1.14 s | 13 ms / 235 ms / 2.23 s | **13 ms / 81 ms / 2.07 s** | p95 < 200 ms ✅ |
| MongoDB operations during the run | 101 | 101 | **301** | |

Save p95 is under the target for the first time, but this session didn't touch the save path,
so read it as variance in the cold-start burst rather than an improvement. As in v3, k6 signs up
all 100 users and their first saves arrive together with an empty session cache. How much that
one burst spills from p99 into p95 differs between runs. Steady-state saves were unchanged. The
p99 (~2 s) is that same burst.

The tripled MongoDB count isn't the save path. The 100 sign-ups in the test's setup now each
publish `user.registered.v1`, and code-service handles each one with a duplicate check, a
starter-project insert and a processed-event record (about 200 extra operations). Saves still
reach MongoDB only through the flusher.

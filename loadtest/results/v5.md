# v5: final (after Session 6)

Same scenarios, settings and hardware caps as every earlier run (0.5 CPU / 512 MB per app
container, fresh processes). Session 6 changed the save path: a fix for edits lost mid-flush,
and saves/reads falling back to MongoDB when Redis is down. The contest soak was run twice to
tell a change from noise.

| Throughput | 24 req/s | 44.9 req/s | 44.4 req/s | **44.4 req/s** | |

## Contest soak: 100 users autosaving every 10s (5m)

| Metric | v0 | v3 | v4 | **v5 (run 1)** | **v5 (run 2)** | Target |
|---|---|---|---|---|---|---|
| Failed requests | 0% | 0% | 0% | **0%** | **0%** | < 1% ✅ |
| Save p50 | 100 ms | 13 ms | 13 ms | **22 ms** | **13 ms** | |
| Save p95 | 1.78 s | 235 ms | 81 ms | **194 ms** | **197 ms** | < 200 ms ✅ |
| Save p99 | 5.67 s | 2.23 s | 2.07 s | **1.23 s** | **2.21 s** | |
| MongoDB queries during the run | 2,916 | 101 | 301 | **302** | **301** | |

- **Save p50:** run 2 matched v3/v4, so run 1's 22 ms was run-to-run noise rather than a cost
  of the Session 6 changes.
- **Save p95:** about 195 ms in both v5 runs, just under the target. The tail is set by the
  cold-start burst described in [v3](v3.md): k6 signs up all 100 users, then their first saves
  arrive together with an empty session cache. How far that burst reaches into p95 varies, and
  v4's 81 ms looks like the favourable end of that range.
- **MongoDB update counts aren't comparable with earlier runs:** the flusher now uses
  `updateOne` (counted as an update) where it used `findAndModify` (counted as a command). The
  number of writes didn't change, and queries match v4.

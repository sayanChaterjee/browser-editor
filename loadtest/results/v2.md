# v2: after Session 2 (cleanup, shared packages, metrics)

Same scenarios, settings and hardware caps as [v0](v0.md) and [v1](v1.md) (0.5 CPU / 512 MB per app
container, fresh processes). New in this run: Prometheus scraped every service throughout, so the
server-side breakdown below comes from the services' own metrics. Dashboard during the run:
[v2-grafana.png](v2-grafana.png).

Note: a disk cleanup (Docker build-cache prune, npm cache clean) ran on the host during the contest
soak, so that phase's tail latency is, if anything, slightly pessimistic.

v2 is at or better than v1 everywhere: the Session 2 refactor (shared packages, monorepo builds,
config validation) caused no regression. Likely contributors to the gain: auth-service no longer
runs a Redis client it never used, and its producer no longer runs two connection loops.

## Where the time goes (Prometheus, p95 over the run)

| Layer | p95 |
|---|---|
| Gateway, as users experience it | **224 ms** |
| └ gateway → auth-service session check | **152 ms** |
| auth-service `get-session` handler | 37–79 ms |
| code-service handlers (`/save` ~10 ms) | 11 ms |
| user-service handlers | 12 ms |

The services answer in ~11–12 ms; **the session check is most of the gateway's p95**. During the
synchronized save bursts auth-service sits at its CPU cap (peak 50% of the 0.5 CPU limit). This is
the bottleneck Session 3 removes (validate sessions in the gateway or from Redis instead of an HTTP
call per request).
